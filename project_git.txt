    * os talks to the operaring system: file paths, directory, env variables
    * 'sys' talks to the python interpreter/runtime itself

    * '.git/objects'  - everything in git is object - a blob(file content), a tree(a folder snapshot) and a commit - they get stored here as a SHA-1-named object
    * '.git/refs' - this are pointers and not data, 'refs/heads/<branch> holds the commit SHA that a branch currently points to - file containing the 40-char hash
    * '.git/HEAD' - a pointer to a pointer, containfs a line lije 'ref: refs/heads/main'

    * '__name__' every python file has this built in variable, if the file is run directly, it is set to '__main__', so that the functions can run; otherwise it means it has been imported, so the funcitons in the files are called to be used later

        * then decode it using utf-8
        * NOTE :  cat file does not end with a new line but print staement does by default, we need to mention end = ''

    * blob is the git's way to storing the file content, no filename no permissions, just the raw bytes of the files content
    * git is content addressed - it does not care what a file is called or where a file is stored - but only what's inside it
    * if two files in our project with different name and different address but exactly the same content, then they have the exact same blob file, both the filenmaes will just point to it

    * How a blob is created  - take the raw file content - "i am Utsav" -> prefix it with a header -> "blob" + <size in bytes> + "\0" -> "blob10\0i am utsav".
    * SHA-1 hash this entire string -> 40 char hex hash -> blob's id
    * zlib compress the whole string -> import zlib
    * save it to the disk at ".git/objects/<first 2 char of SHA-1 hash>/<last 38 char>
    * So a blob identity is its hash, and its hash is a fingerprint of its entire content(also the small header)
    * even a smallest change - a new sha1 - a new blob object

    * NOTE : why store the <size in bytes> instead of just pure content -> now the pure content can have literal null bytes which are meant to be of the data, but when reading the content, the reader might get confuse, so this is a defined boundary for till when the file must be read

    * NOTE :  why store in a folder with <first 2 hash char> and not directly in the object folder - filesystems become noticeably slow when file number increase, hashing is a very random and evenly distributed function - 2 hex characters can create 256 subfolders - Method called SHARDING/BUCKETING

    * SHA-1 (secure hash algo 1) -> takes anything - a byte, a sentence, a file -> convert to fix size 160 bit -> 20 bytes -> a 40 hex characters. Deterministic-> same input == same hash
    * This is not an encryption -> cannot convert back

    * Zlib compression -  General purpose lossless compression algoritm - puerly for space optimisation

    * Plumbing commands - these are git's low level, internal building-block commands - raw primitives that operate directly on the object database
    * It is opposite to the porcelain command that we use on a daily basis like git init git push git commit
    * hash-object : plumbing command to create a blob from a file and get its hash
    * cat-file : read back an object's raw content, cat means catalog (read the type, size and raw content) -p means pretty print -  just print the content in a readable way 
    * similar are write-tree and commit-tree - plumbing commands

    * partition is safer considering .index and .split both, as .split may split on null characyter present in the actual content
    * decode to convert raw bytes(recoeved from zlib decoompression) into human readable python strings

    PART 1 : REF Discovery - asking a remote server(github) what brances/commit do you have

        * Sending a plain HTTTP GET request to a specific URL - <https://github.com/<user>/<repo>.git/info/refs?service=git-upload-pack>
        * Note above that it is simple github repo link
        * <service=git-upload-pack> is just a query parameter telling github that i am here to download/clone/fetch and not for upload/push
        * git uses same url for both direction clone and push
        * <git upload pack> can sound confsuing, but this is server perspective, it needs to upload objects(a pack)

        * What comes back - a list sayingn (here are all my branches and tags, and here's the exact commit each one points to)
            refs/heads/main       → a1b2c3d4...
            refs/heads/develop    → e5f6a7b8...
            refs/tags/v1.0        → 9c8d7e6f...
        * this tells us which branch is main, and which sha commit we should point at once everything is downloaded
        * the response is respinse object, techincally an http.client.HTTPResponse, it is an open stream
        * we uuse (.read()) to actually pull the bytes out of the stream
        * one extra thing, this response has the very first pkt line as an announcement and not ref list, something loike '# service=git-upload-pack' folowed by a flush

        * It is helpful, so the user can select what do it need before transferring or downloading huge amounts of data on to his system

        * The response is wrapped in pkt-line framing (this is different from plain text) because this is the format that is used to carry any kind of data in response, although here we needed plain readbale text, we can later have raw binary bytes too
        * This (pkt line format) is nothing specifc to ref, its the one wire format the entire protocol reuses everywhere

        * pkt line format - length prefixed framing - 4 hex character length, total byte length of entire line, including prefix
        * continue this process till you have consumed the whole buffer or hit a '0000' -> flush packet

        * Special attention: Github sometimes reject or behave oddly towards requests that don't identify themselves as real browser/tool, as python does normally. So we are sending a User-Agent that look like a normal git client(git/2.0.0)

        * Now the tuff part - per-object headers and variable length encoding
        * Objext header format - (variable length header - this encodes <type> and <uncompressed size>)
            * First byte :
                bit 7 (MSB) - continuation flag
                Bits 6-4 (3 bits) - type
                Bits 3-0 (4 bits) - the lowest 4 bits of the size
            * Each subsequent bit - only if continuation flag is set
                bit 7 (MSB) - continuation flag again
                Bits 6-0 (7 bits) = the next chunk of the size, added on top of what you've accumulated so far.
        * Type values:
            1 = commit, 2 = tree, 3 = blob, 4 = tag, 6 = OFS_DELTA, 7 = REF_DELTA
            5 - reserved/unused - ignore for now
        * Now while parsing the header, we will need to parse byte by byte for info like type and size
        * will use bit manipulation for the same, interesting
        
        * Now this header parsing is crazy, we will start with an offset, will pick the byte at that offset
        * Now play with bit manipulation
        * For object type (3 bits) (bits 6-4) (type can be 1-7), do (byte >> 4) & 0111
        * For size (4 bits) (bits 3 -0) do (byte & 1111)
        * And the crazy thing about size is these four bits are the lowest significant bits in the actual size bit, this means if the size is greater, then continuation flag will be set, and the 0-6 bits of the next byte will be left shifted and orred with the previous one to get the size, and if the size is even larger, will keep on doing this depending upon the continuation bit
        * In this process we will keep the track of offset which will changed by one after analying a byte and Size shift which will be +4 for the first bit and +7 for the upcoming bits
        * this size is of the decompressed data
        
        * After all this object header we have the compressed data
        * Now note that we know the uncompressed size but we have the compressed data now
        * Will leave this work for the zlib library to figure out, we will provide the entire remaining data

        * Object type not studied yet - (tag, OFS_DELTA, REF_DELTA)

        * Now we have worked on the normal objects, blob, tree and commits, now we will work on OFS_DELTA 
        * for each OFS_DELTA object we need to: (1) read how far back its base object is, (2) find that base (already resolved, sitting in memory), (3) apply the delta's copy/insert instructions against it to reconstruct the real content.
        * Right after the type+size header you already parse, OFS_DELTA objects have one more variable-length field — the negative offset to the base object — using a similar-but-not-identical continuation-bit encoding
        * The base object starts result bytes before where the delta object's header began. Since we'll need to know where each object's header started (not just where we are now), we need to track that separately — the main loop needs a small change to remember starting offsets.

        * Applying the delta instructions, parsing the instructions
        * Every instruction byte's top bit tells us which kind it is — 1 = copy (from base), 0 = insert (new literal bytes follow)
        * For COPY: the lower 7 bits of that instruction byte are themselves flags — each bit says "is this particular byte of offset/size present, or assumed zero?" — this is another space-saving trick (why send 4+3=7 bytes for offset+size every time, when most deltas only need 1-2). 
        * For INSERT: dead simple — the byte's value is the length, followed by exactly that many literal bytes to copy in directly.

        * Wiring it into the main loop — this needs restructuring since deltas must resolve after all objects are read (their base might appear later in iteration order isn't guaranteed to be exactly correct... actually OFS_DELTA bases always come earlier in the file by construction, so single-pass mostly works, but let's be safe and do two passes)
